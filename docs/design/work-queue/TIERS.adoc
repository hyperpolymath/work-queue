toc::[]

== Ground rules for every tier

* *Spec first.* Any behaviour that changes or adds a state transition goes
  into `WorkQueue.tla` first, is model-checked by `just wq-oracle`, and only
  then is coded. Never edit the core to "fix" a conformance failure without
  showing that the spec agrees.
* *Green means green.* `just wq-conformance` passes, and `just wq-mutants`
  keeps 0 survivors. Add a mutant for every new guard you write.
* *Functional core, imperative shell.* `src/core/queue.zig` stays pure: no
  clock, no I/O, no allocation. Time, files, processes and HTML live in the
  shell and reach the core only as actions.
* *One action per persisted change.* The store is an append-only event log.
  Current state is the fold of the core's `step` over the log, so every
  persisted change goes through the checked transition function. That is a
  claim about the code path, not about coverage: the conformance check is
  exhaustive only for the finite models it was run on (MC.tla: three jobs
  for the contract rules, four jobs of one priority for the share rule; two
  workers each). States with more jobs or other declared
  facts are reached through the same `step`, but no graph covers them.
* Zig 0.17.1. No banned estate languages (no Python, Go, TypeScript, Nix).
  JSON written by the tool is I-JSON serialised by JCS (RFC 7493, RFC 8785),
  one record per line in `.jsonl`.
* No ABI or FFI boundary in the MVP: it is one Zig binary. If one is ever
  exposed (for example to BoJ), its ABI proofs in Idris2 are mandatory.
* Report faithfully: an unexecuted check is never a pass.

== Shared interfaces

Tier 1 owns these. Tiers 2 and 3 build against them as written here; a change
is made in this file first, in the tier 1 PR.

=== Store

`$WQ_HOME`, default `$XDG_STATE_HOME/work-queue` (`~/.local/state/work-queue`):

* `jobs/<id>/<rev>.toml`: the job record from CONTRACT section 2. A revision
  is immutable once written. The owner edits a job by writing a new
  revision, and `q amend` records it as an event. Keys: `id` (letters,
  digits, `-` `_` `.`), `title`, `category` (a key of the host's `shares`),
  `priority` (1..4), `owner`, optional `repos`, `limits`, `heavy` (default
  `true`: a job takes a heavy slot unless it says otherwise) and `obligation`
  (default: the id; jobs with one obligation never run together), and
  `[admission]`. Unknown keys and a `[state]` table are refused: state lives
  in the log. The core's `Need` is `admission.resources.ram_gib` rounded up
  to whole GiB. `admission.checkpoint` must state the behaviour; the value
  `"none"` states there is none, so the job cannot be preempted (`Ckpt`).
* `host/<rev>.toml`: `capacity_gib`, `heavy_slots`, `probe_gib`,
  `reject_limit`, `workers` (named `w1`..`wN`), `lease_ttl` (like `15m`) and
  a `[shares]` table of category = positive integer weight. Integers keep the
  share comparison exact; a category's target is its weight over the sum.
  Immutable per revision, like jobs.
* `events.jsonl`: append-only, one I-JSON/JCS object per line, `seq` dense
  from 1. Shapes (keys in JCS order):
  `{"action":"start","at":"<RFC 3339 UTC>","job":"<id>","rev":3,"seq":<n>,"worker":"w1"}`;
  other job actions drop `worker`; `rev` is the job revision in force, and a
  log naming any other revision does not replay. `add` and `amend` carry the
  new revision; `host_amend` carries the host revision and no `job`;
  `host_hold` and `host_release` carry only `action`, `at` and `seq`.
  Actions: `host_amend`, `add`, `amend`, `record`, `admit`, `start`, `beat`,
  `lease_lapse`, `checkpoint`, `accept`, `reject`, `preempt`, `hold`,
  `release`, `drop`, `host_hold`, `host_release`.
  Writers hold an exclusive `flock` on the log for read, check and append;
  readers take a shared one. A log that does not replay through the same
  guards (a refused event, a sequence gap, a torn last line) is an internal
  error, exit 1: the tool never folds past it.

Replay uses, for each event, the job and host revisions that were current
when it was appended, so editing a record never changes how history folds.
Revisions change the spec's constants (`Need`, `Prio`, `Obl`, `Cap` and the
rest), so `amend` and `host amend` are spec work, done before they are coded.
Until then they are refused unless every job they affect is `queued` or
`dropped`, and a host revision may never set `Cap` below the reserved total.
A host revision affects every job, but a `completed` job has no action left,
so `host amend` is allowed when every job is `queued`, `completed` or
`dropped`, and it may not drop a category a job uses.

Leases live in the shell, because the model has no clock. A lease's expiry is
the time of its latest `start` or `beat` event plus the TTL of the host
revision in force at that event. `q tick` compares that against the clock
and appends one `lease_lapse` event per expired lease. Every mutating verb
runs it first. The read-only verbs (`board`, `gate`) never write, so they
show an expired lease as expired until the next tick lapses it.

=== CLI: `q`

Every mutating verb is exactly one core action, applied only if the core
enables it. On success it prints `<seq> <action> [<id>]` per appended event
(implicit lapses included). `WQ_NOW` (RFC 3339 UTC) replaces the clock, for
tests.

[cols="1,1,3",options="header"]
|===
|Verb |Core action |Notes
|`q add <file.toml>` |none |stores revision 1; the job starts `queued`
|`q amend <id> <file.toml>` |none yet |new revision; spec work first (see Store)
|`q record <id>` |Record |refused until all seven admission fields are set
|`q gate <id>` |none |read-only: says which guard blocks Admit, in words
|`q admit <id>` |Admit |
|`q start <id> --worker <w>` |Start |grants a lease with the host TTL
|`q beat <id>` |Beat |durable event; extends the lease to now + TTL. Beat is
a stutter in the spec (the model has no clock), enabled only while running
|`q tick` |LeaseLapse for each expired lease |also run implicitly by every verb
|`q checkpoint <id>` |Checkpoint |records the measurement
|`q accept <id>` / `q reject <id>` |Accept / Reject |
|`q preempt <id>` |Preempt |added in tier 1: the spec's Preempt had no verb.
Enabled only for a running checkpointable job while a more urgent job is ready
|`q hold <id>` / `q release <id>` / `q drop <id>` |Hold / Release / Drop |
|`q host amend <file.toml>` |none yet |new host revision; revision 1 must exist
before any job is added (see Store)
|`q host hold` / `q host release` |HostHoldOn / HostHoldOff |
|`q board [--json\|--html]` |none |read-only view; plain text without a flag;
`--html` exits 2 until tier 3 builds it
|===

Exit codes: `0` done; `3` refused because the action is not enabled, with the
blocking guard named on stderr; `2` usage error; `1` internal error.

=== Board JSON (`q board --json`, schema `work-queue/board/v1`)

----
{"categories":[{"name":"proofing","share_target":0.4,"share_used":0.25}],
 "generated_at":"<RFC 3339>",
 "host":{"cap":4,"heavy_running":1,"hold":false,"reserved":3,"slots":1,"workers":2},
 "jobs":[{"category":"proofing","id":"...","lease":{"expires_at":"...","worker":"w1"},
          "line":"Progress: running on w1, lease 12m left","measured":false,
          "owner":"chat:...","priority":1,"reason":"none","rejects":0,"res":2,
          "state":"running","title":"..."}],
 "schema":"work-queue/board/v1"}
----

Keys are JCS-sorted. `line` always starts `Waiting:`, `Held by:` or
`Progress:` (rule R2: every non-running job says why it waits). `lease` is
`null` unless the job is running. `categories` are sorted by name
and `jobs` by id. `share_target` is the weight over the sum of weights.
`share_used` is the category's part of the reservation held *now*
(`Used(c)` over the reserved total, 0 when nothing is reserved): the quantity
the admission tie-break compares. It is not a trailing-7-day figure as in
`board-mock.html`; that needs the share unit chosen (CONTRACT section 6).

== Tier 1: ledger and gate

Suggested model: top tier (spec extension and core generalisation are proof
work).

. Generalise `Queue(comptime n)` to a job table of any size. The conformance
  test keeps n = 3, and both oracles stay green.
. Add category shares to the spec as a tie-break among equal priorities.
  Model-check it, extend the oracle and harness, then code it.
. Event-log store, `q` CLI and `q board --json` as specified above.
. Tests: conformance, mutants, plus CLI golden tests replaying an event log.

Done when every verb works end to end on a scratch `$WQ_HOME`, the conformance
and mutant checks are green, and the board JSON validates against this file.

Status (tier 1 PR): `just wq-conformance` (three oracles), `just wq-mutants`
(23 mutants, 7 of them on the share guard) and `just wq-cli` (golden
scenario of every verb, replay, board shape against this file, I-JSON/JCS,
and three logs that must not replay). Category shares are a tie-break on the
reservation held now; see the spec README for why, and for what a deficit
scheme would need first. Not done in tier 1: modelling revisions (so `amend`
stays restricted), recording the checkpoint's measured size (the spec's
`Need` is a constant), and a CI workflow for these recipes.

== Tier 2: launching under limits

Suggested model: Sonnet. Depends on the tier 1 CLI; until that lands, build
against the verb table above behind a thin interface.

. `q run <id> --worker <w>`: performs `start`, then runs the admission command
  in its `cwd` under
  `systemd-run --user --scope --unit wq-<id> -p MemoryMax=<ram> -p CPUQuota=<cpu*100>%`.
. Heartbeat every TTL/3 with `beat`. Process exit leads to `checkpoint`; the
  owner or a validator then accepts or rejects.
. On preempt, hold or lease lapse: SIGTERM, a grace period, then
  `systemctl --user stop wq-<id>.scope`.
. A `--limiter none` mode and a `--dry-run` mode that prints the exact argv,
  for CI and for hosts without a systemd user session.
. Windows Job Objects: designed, not built.

Evidence: unit tests with a fake limiter in CI. A real cgroup acceptance run
(a memory hog is killed at `MemoryMax`) needs a Linux host with a systemd
user session that the owner names. Not The-Titanic while it is memory-starved.

== Tier 3: live board

Suggested model: Sonnet or Haiku. Depends only on the board JSON above, so it
can use a fixture until tier 1 lands.

. `q board --html` writes one static page from the board JSON, following
  `board-mock.html`: headroom strip, category share meters with target ticks,
  seven state columns, and one `Waiting:`/`Held by:`/`Progress:` line per card.
. `q board --html --watch` regenerates when `events.jsonl` changes; the page
  carries a meta refresh. No server and no listening port in the MVP.
. Plain HTML and CSS. Plain JavaScript only if it is needed.
. Golden tests: fixture JSON in, exact HTML out. One accessibility pass
  (contrast, headings, no colour-only state).

== Not in the MVP

Cloud workers, spending limits, the BoJ coord-bus bridge, Windows runner,
`q serve`, multi-host. Each of these is a separate decision for the owner.
