= Work-queue spec, model check and conformance oracle

`WorkQueue.tla` models the job contract (`docs/design/work-queue/CONTRACT.adoc`,
sections 3 and 4): states, leases, reservations, heavy slots, obligations,
priorities, category shares, probes, preemption, holds, heartbeats and the
reject limit. It is the oracle
the Zig core (`src/core/queue.zig`) is checked against.

Rebuild everything with `just wq-conformance` (Java 17+, Zig 0.17.1). The TLC
jar is fetched from the v1.8.0 release and pinned by SHA-256 in
`scripts/wq-oracle.sh`.

== Model-check results (TLC 1.8.0, models in `MC.tla`)

Model 1: three jobs (j1 urgent and heavy; j2 normal and heavy; j3 low and light,
sharing j2's obligation), two workers, capacity 4, one heavy slot, probe cap 2,
reject limit 2. Its priorities are distinct, so the share tie-break never
decides in it; adding shares left all four of its state counts unchanged.

Model 2: four light jobs of one priority, two categories with weights
a = 2 (j1, j3) and b = 1 (j2, j4), two workers, capacity 6, probe cap 2.
j1 and j2 share an obligation and j4 needs 5 GiB once measured, so each
conjunct of the share rule has a reachable state where it alone decides
(see the comment in `MC.tla`). A first version with distinct obligations
let the "share rival ignores obligation" mutant survive; that is how the
gap was found.

The as-drafted failure is the finding that justifies the reject limit. j1 is
rejected at checkpoint, returns to `ready`, is re-admitted, and is rejected
again for ever. Because j1 is the most urgent ready job, j3 is never admitted:
one repeatedly rejected job starves every job below it. With the limit, j1 is
held with reason `reject limit` after two rejects and needs an owner edit.
`scripts/wq-oracle.sh` fails if this counterexample ever disappears.

`rejects` is a saturating counter at `MaxRejects`. Nothing reads it above that
value, so this keeps every behaviour while making the state space finite;
an unbounded counter is why the first TLC runs never finished.

Scope limits (reported, not hidden): the model has no clock (a lease lapse is
an action the shell triggers) and fixed declared facts per job, so job and
host revisions are not modelled. `SharesSafety` uses reject limit 1 to keep
the graph to 217,440 states (in the first version of model 2, limit 2 gave
1,158,864 states against 255,196 with limit 1);
reject cycles are covered by model 1, and `SharesLive` keeps limit 2. Results hold for this finite model only; they are bounded model
checking, not a proof for all job counts.

== Category shares

Contract rule 5: share is a tie-break inside one priority, never an
override of it. The spec's rule (`ShareFirst` in `Admit`): among *eligible*
ready jobs of equal priority (ready, fits, obligation free), admission goes
to a category whose current reservation is lowest relative to its weight,
`Used(c) / Weight[c]`, compared by cross-multiplying so it is exact. Ties
stay nondeterministic; share never preempts.

Why this and not a deficit (debt) scheme:

* It reads only `res`, which the spec already has. No new variable, so the
  graph can only lose `Admit` edges, and model 1 proves it changed nothing
  where priorities differ.
* A historical deficit needs a clock or counters that grow without bound;
  TLC would then need a saturation that changes behaviour. It also needs
  the unit question in CONTRACT section 6 (lease minutes or GiB-minutes)
  settled first; this rule does not.
* Progress: among eligible jobs at the most urgent priority, one with the
  least ratio always exists, so the tie-break never blocks every candidate.
  `SharesLive` checks this under weak fairness.

What it gives up: it is fair in the moment, not over history. A category
whose jobs finish fast can win again and again against one that holds its
reservation for longer. A deficit scheme fixes that once the unit is chosen.

Observation, not changed here: the *priority* guard in `Admit` counts a more
urgent ready job that fits even when its obligation is busy, so it can hold
back less urgent jobs while it cannot itself be admitted. Liveness still
holds (the busy obligation's job finishes), so it is head-of-line waiting,
not starvation. The share guard counts only eligible jobs, so it does not
do this. Aligning the priority guard is a spec change for the owner.

== Oracle format v1

`oracle.awk` turns a TLC dump (`-dump dot,actionlabels`) into plain lines
(`awk -v NJ=<jobs>`, default 3; TLC wraps long values over several label
lines, which `oracle.awk` joins):

----
S <id> <hostHold 0|1> then, per job j1..jNJ: <st> <reason> <lease> <res> <measured 0|1> <rejects>
I <id>                          the initial state
E <from> <to> <Action> [job] [worker]
----

Reasons use `_` for spaces (`no_record`). Ids are dense and 1-based but not in
file order. `E n n Next` lines are the stutter steps of finished states and map
to no core action. Every (state, action) pair has exactly one successor.

== What conformance checks (`tests/conformance/conformance.zig`)

For all three oracles (model 1 as drafted and with the limit, model 2):

. every edge `s --A--> t` gives `step(s, A) == t`;
. in every state, the set of actions the core enables equals the set of edges
  leaving it, so the core has no extra and no missing moves;
. in every state, the core's own rule checks (`brokenRule`) pass.

It also checks that the oracle's one initial state is exactly a fresh core
queue.

Last run: 70,688 states and 492,436 transitions (as drafted), 38,244 states
and 256,886 transitions (with the limit), and 217,440 states and 1,873,120
transitions (model 2), all matching.

`tests/conformance/mutants.sh` plants one rule break at a time in the core.
It first requires the unmodified core to pass, and counts a mutant as caught
only if it compiles and then fails conformance; a mutant that does not
compile is reported as invalid and fails the run. Last run: 23 mutants,
23 caught, 0 survived, 0 invalid: the 16 from PR #1 (retargeted at the
generalised core, same meaning) and 7 on the share guard, one per conjunct
(the whole guard, weights, strict comparison, equal priority, and the
rival being ready, fitting and obligation free). Run with `just wq-mutants`
(about 12 minutes).

Correction: the first version of this script (PR #1) reported 15 of 15 caught,
but its "admit ignores priority" mutant did not compile, and the script
counted the compile failure as a catch. The priority rule was therefore not
mutation-tested in that run. Found in review; fixed, and now caught.
